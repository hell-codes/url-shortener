How Slotly works

This page walks through every Data Structures concept behind the app/site.

Concept

URL shortening

URL shortening maps a long, hard-to-share URL to a short alphanumeric code. When someone visits the short link, the server looks up the code and redirects to the original URL.

The interesting engineering problem is not the redirect itself — it's how the mapping between "short code" and "original URL" is stored and looked up quickly, even as the number of links grows.

Concept

Why a hash table?

A hash table gives average-case O(1) insert, search, and delete — exactly what a lookup-heavy service like this needs. Instead of scanning a list of every short code, the hash table jumps almost directly to the right slot.

Slotly implements this hash table manually, using a plain array as backing storage, instead of relying on Python's built-in dictionary — so every step of hashing and collision handling is visible and explainable.

Concept

The hash function

The hash function converts a short code's characters into a single integer, then reduces it into a valid array index using the modulus operator against the table's capacity.

index = (hash × 31 + charCode) % capacity, applied character by character

Concept

Collisions

A collision happens when two different short codes hash to the same array index. Since the table has a fixed number of slots, this is unavoidable once enough entries are inserted — the table must resolve where the second code actually goes.

Concept

Linear probing

When a slot is already occupied, linear probing checks the next slot, then the next, wrapping around the end of the array, until it finds an empty or deleted slot. Deletion marks a slot as a tombstone rather than clearing it, so later searches can still walk past it to find entries that were probed further along.

Concept

Why linear probing?

Linear probing was chosen over chaining because it keeps every entry inside one contiguous array — no extra linked lists or pointers — which makes the data structure easier to visualize, easier to persist to JSON, and easier to explain step by step.

Flask receives a GET request for the short code, searches the hash table, increments the click counter, and issues an HTTP 302 redirect to the original URL.

Every insert, delete, and click update is written to a JSON file. On startup, Flask reads that file and rebuilds the hash table from it.

It mirrors a real REST architecture: the frontend is a static site that only talks to Flask through JSON APIs, so either side can be replaced or redeployed independently.
